## 方案 A：隔离验证应用绘制候选列表

需要用户明确允许“自绘候选”的范围变更。输入法仍负责组词、候选内容和提交；框架仅负责候选列表呈现。先验证隔离工具，不迁移生产。

1. 使用 TSF UILess 协议，在 BeginUIElement 返回不显示原生 UI；在 UpdateUIElement 后读取候选内容、选择和分页。不得假定 Begin 时内容已就绪。
2. 不调用 Show(TRUE) 恢复原生候选；保持活动元素生命周期，在应用自己的显示层中显示、隐藏并恢复列表。
3. 以现有输入区域与祖先裁剪交集控制列表可见性。完全裁出时停止显示，恢复时读取当前活动元素状态，不缓存已经 End 的 COM 对象。
4. 第一轮仅验证键盘选词、真实候选更新与显示连续性。鼠标选词和生产 API 需要另行设计，不以静态候选图片代替可工作的输入法。
5. 只处理确实支持相应接口的输入法；不支持时明确报告能力不足，不冒充等价支持。

真实验收必须保持完整组合、同一组合会话、测量期间 begin/end 计数不变及绑定写入为零；检查滚动前、完全裁出、恢复后的窗口与整屏截图。然后通过真实中文选择和唯一提交验证输入法仍工作。仅 UIElement 存在、HRESULT 成功或候选文字能读出，均不能算通过。

这是尚未验证的可行性方案，不能承诺当前微软拼音一定支持完整候选行为。

## 方案 B：调整交互规则，组合期间保持输入区域可见

需要用户接受改变原先“完全裁出后隐藏并恢复候选”的交互要求。通过滚动策略保持组合输入区域可见，避免进入已知失败场景；必须同时设计滚轮、布局变化及窗口变小的行为。这不能标为原隐藏门槛通过，必须明确修订任务和用户可见行为。
