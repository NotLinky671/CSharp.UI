# Codex：TI-07 审核与推进失误复盘

记录日期：2026-10-21

适用范围：Codex 对本项目的任务规划、DSH ACP 实现协调、独立审核与验收。

本记录回应用户对耗时和反复返工的反馈。实现由 DSH 完成，但任务粒度、证据要求、返修节奏和验收结论由 Codex 负责。不能把耗时全部归因于 TSF 复杂、实现模型或环境限制。本文不是交付记录，也不关闭任何尚未通过的任务。

## 1. 我没有尽早建立最小的真实使用闭环

现象：底层协议、会话和大量单元测试通过后，正式宿主仍出现旧桥引用、客户端切换未更新底层会话、默认普通输入被队列吞掉等问题。

我的失误：把较多时间投入底层覆盖，过晚要求通过正式宿主自己的输入适配器、运行时和 TextField 验证完整链路。只看到模块分别正确，不能推出模块连接正确。

后续规则：每次接入先通过一个最小纵向场景：真实宿主创建 → 聚焦真实字段 → 输入 → Binding 回读 → 释放。涉及焦点时立即增加第二个字段，验证旧归属结束、新归属建立和后续文字去向。默认后端的普通输入必须最先检查，不能等新后端测试全部完成后才检查。

## 2. 我派发的实现批次过大，返修目标持续增加

现象：P3a 同时要求原生接口、钩子、服务生命周期、输入顺序、回退和多个工具。一个批次交回时只完成其中一部分；随后又进入较大返修批次。

我的失误：虽然列出了详细要求，却没有把它们变成可在一轮内完成、独立验收的交付边界。后续任务文本又逐渐变长、重复，降低了执行重点的清晰度。

后续规则：一次只设一个主要行为门槛，说明当前失败、最小复现、允许修改范围、准确退出条件。关联边界保留在主计划，当前任务只链接它们。前一门槛未通过，不以增加更多实现范围替代修复。新增缺陷标明阻塞程度和所属批次，避免无限扩张当前任务。

## 3. 我没有足够早地验证测试本身能发现错误

现象：探针把 WH_GETMESSAGE 的返回值 1 当成消费消息，又将 VK_C 的 0x43 与 WM_CHAR 的字符值比较，漏检小写 c（0x63）；曾得到“没有回声”的假通过。部分测试只看队列数量，未检查文字真正进入输入框。

我的失误：接口语义和断言有效性核查得太晚。后来独立审核发现问题，不抵消前期错误测试造成的时间浪费。

后续规则：关键原生机制先查官方契约，确认接口签名、返回值和消息修改方式。每个高风险验收至少有一个负向对照：故意撤掉被验证的修复，断言必须失败。输入验证检查最终文字、字段归属、写入次数和队列清空；回调计数、类型名称、布尔标志只能作辅助证据。

## 4. 我没有严格区分替身验证、原生机制验证与产品接入验证

现象：创建了真实 OpenTK 窗口，却用工具自己的 PeekMessage 循环；另建 headless runtime 的 TextField，被用于描述正式宿主接入；工具函数叫“同泵顺序”，实际只投递 A/C，未执行中文确认或切换第二字段。

我的失误：要求中的“真实”没有始终落实为可追踪的实际对象与调用链，过晚发现证据覆盖范围与名称不一致。

后续规则：每项证据明确入口、使用的产品对象、注入的替身和实际触发的路径。正式接入必须经过宿主自己的 GLFW 消息泵、输入适配器、runtime 和 TextField。场景步骤未执行即未覆盖；需要 TSF 的场景不能在 TSF 未建立时 note-and-pass。测试名称不得超出断言内容。

## 5. 我允许关键缺陷未关闭时反复跑大范围回归

现象：多轮 Debug/Release 和七组审计通过，但当前新增的默认输入、延后重放、两字段交错场景仍未通过或根本未实现。

我的失误：没有在协调执行时及时限制重复验证。大量绿色计数掩盖了当前阻塞项没有变化，也消耗了时间。

后续规则：固定次序为“失败复现 → 修复 → 定向行为检查 → 相关回归 → 阶段完整验收”。定向门槛未过，先处理失败；相同代码且没有新风险时不重复全量检查。汇报优先说明阻塞行为的结果，不以总测试数表示完成度。重复包装运行的场景按去重后统计。

## 6. 我对构建与环境问题的诊断不够及时

现象：失败构建后曾运行旧 DLL；恢复文件的时间戳导致增量构建跳过；新工具因还原失败反复尝试 HintPath、手工复制 DLL、关闭 deps 文件。后来我用正常 ProjectReference 成功还原，说明不能把先前失败直接概括为项目引用不可用。

我的失误：没有更早终止环境猜测和绕行，也曾直接运行已经被清理的临时项目路径，得到“项目不存在”的无效尝试。

后续规则：先检查项目存在、完整命令、真实退出码和实际错误。构建失败即停止运行对应测试；需要时强制重建独立输出，确认执行路径与当前产物一致。环境失败保留最小项目和日志，由 Codex 复核或按权限要求执行，不能立即归因于缓存只读。验收工具保留正常项目引用，不把临时复制产物方案变成永久结构。DSH 修改期间不并发构建共享产品输出。

## 7. 我记录了许多问题，却没有把反馈收敛成足够明确的下一步

现象：同一审核文档不断追加增量，活动状态中残留过期进程信息；实现方需要从长历史里寻找当前阻塞项。部分派发文本还残留了错误的其他项目工作目录。

我的失误：证据保存较多，但执行依据缺少及时整理，文档数量和长度没有转化为更有效的推进。

后续规则：保留审核历史，同时在文首维护当前问题表，包含 ID、状态、失败证据、验收条件。每轮只派发当前需要关闭的条目。任务头检查仓库路径、模型、范围、报告位置和禁止提前执行的下一阶段。状态文件记录最后更新时间与活动进程是否已结束，不让历史“active”充当实时状态。

## 8. 我的进度表达有时比证据更乐观

现象：使用“已经解决”“整条链通过”等说法时，部分结果仅来自 DSH 报告或较窄的合成场景；后续仍需纠正覆盖范围。

我的失误：没有始终清楚地区分实现方报告、Codex 独立复测和阶段验收。持续发送细碎更新，也增加了用户理解成本。

后续规则：明确使用“DSH 报告通过”“Codex 独立复现/复测通过”“阶段验收通过”。每次更新只说明新增结论、当前阻塞和下一项能消除的不确定性。没有新结果时不重复测试计数或宣布进展。P2 通过不表示 P3 通过，原型通过不表示生产接入通过。

## 后续每轮执行前的检查

- 当前最重要的用户行为是什么？是否已有最小失败复现？
- 任务是否只有一个明确的主要交付门槛？路径和模型是否准确？
- 断言是否检查真实结果，负向对照是否会失败？
- 是否经过实际产品调用链？替身和未覆盖部分是否写清？
- 当前阻塞尚未关闭时，是否又在重复大范围回归？
- 交回后是否基于稳定源码和新产物独立复测？
- 审核状态、派发任务和对用户的说明是否一致？
